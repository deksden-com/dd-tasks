# Git при работе с Банком памяти

Этот блок читают промпты, которые анализируют, чинят или обновляют Банк памяти.

Если операция создаёт Git commit, tag, push evidence, merge evidence or branch/worktree cleanup, также применяй единый Git operation context из `common/git-ops.md`, включая route vs delivery fixation, project policy sources, cleanup/continuation policy and commit trace tags. Этот файл уточняет Memory Bank modes, но не заводит отдельный формат Git evidence.

Работа с Банком памяти должна происходить в той ветке, где результат будет использован:

- фича или протокол - текущая feature-ветка;
- закрытие `DEF-*` перед merge - текущая feature-ветка;
- общий ремонт Банка памяти - согласованная рабочая ветка;
- инициализация Банка памяти - отдельная init-ветка или текущая рабочая ветка проекта по явному решению;
- апгрейд канона - ветка и merge-путь по проектной Git-политике; отдельная upgrade-ветка является безопасным режимом по умолчанию для больших апгрейдов;
- lint Банка памяти - текущая ветка допустима, если проверка не меняет активные документы;
- read-only аудит - текущая ветка допустима, если аудит не меняет Банк памяти.

## Предварительный контроль

Перед анализом или изменением Банка памяти проверь:

```bash
git branch --show-current
git status --short
git rev-parse HEAD
git rev-parse --abbrev-ref --symbolic-full-name @{u}
```

Если upstream отсутствует, зафиксируй это в отчёте и действуй по проектной политике.

Также выясни по Банку памяти проекта:

- какая ветка считается интеграционной: `develop`, `main` или другая;
- где описан поток Git (git flow);
- есть ли правила для рабочих деревьев (worktree);
- какая ветка должна стать текущей после merge/delivery;
- нужно ли удалять локальные и удалённые временные ветки после успешной доставки;
- какие изменения уже были до начала работы.

## Режимы

### Read-only audit

Используется для `mb-audit` и других проверок без правки активного Банка памяти.

Правила:

- Git-preflight обязателен.
- Чистое дерево желательно, но не обязательно.
- Не меняй активные документы Банка памяти.
- Можно создавать рабочие артефакты в `.tasks/`.
- Если дерево грязное, зафиксируй это в отчёте: какие изменения уже были и могут ли они влиять на выводы.
- Не делай вывод "проектная истина изменилась", если видишь только незакоммиченный локальный черновик.

### Memory Bank fix

Используется для `mb-init`, `mb-fix`, `workers/docs.md`, `def/fix.md`, `code/readiness.md` и других правок Банка памяти.

Правила:

- Git-preflight обязателен.
- Ветка должна быть понятна: feature, текущий протокол, dedicated docs branch или интеграционная ветка по проектной политике.
- Если есть чужие изменения, не трогай и не откатывай их.
- Если есть изменения в `.memory-bank/`, сначала выясни, это часть текущей работы или чужой контекст.
- Если изменения пересекаются с твоей задачей, работай поверх них только после понимания смысла.
- Если состояние слишком грязное для безопасной правки, остановись и попроси пользователя выбрать: закоммитить, отложить, создать отдельную ветку или продолжить с риском.
- Перед коммитом добавляй только файлы текущей работы.
- Сообщение коммита должно использовать trace tag из `common/git-ops.md`: `[PRT-XXX/stage]` для протокольной работы или `[RUN-XXX/stage]` для `mb-init`, `mb-upgrade`, `mb-fix` и других operation runs без одного протокола.

Для больших независимых правок `mb-fix` может создать несколько рабочих деревьев (worktree). Это разумно, если группы исправлений пишут в разные целевые папки и выигрыш от параллельной работы выше стоимости последующего merge. Если правки пересекаются по файлам, лучше выбрать последовательный режим.

### Memory Bank lint

Используется для `mb-lint`.

Правила:

- Git-preflight обязателен.
- Проверка может выполняться на грязном дереве, если отчёт явно указывает, что проверялось текущее локальное состояние.
- `mb-lint` не должен менять активные документы без отдельного режима fix.
- Если инструмент предлагает автоматические исправления, применяй их только через `mb-fix` или явную задачу на правку.

### Memory Bank upgrade

Используется для `mb-upgrade`.

Правила:

- Чистая базовая точка обязательна.
- Стартуй от интеграционной ветки проекта, если проект не говорит иначе.
- Создай отдельную upgrade-ветку, если проектная политика требует branch/PR/merge или если политика неясна. Если проект явно разрешает прямой memorybank-upgrade в интеграционной ветке, можно работать прямо там и затем зафиксировать, что отдельная merge-стадия не нужна.
- Target-пакеты выполняются в отдельных рабочих деревьях (worktree).
- Не начинай worktree-миграцию поверх грязного дерева.
- Если в целевом проекте есть незакоммиченные изменения, сначала добейся решения: коммит, stash, отдельная ветка или остановка.
- Если проектная политика не объясняет cleanup временных веток/worktrees или ветку продолжения после merge, спроси пользователя до создания upgrade/target branches. Не создавай временные ветки "потом разберёмся".
- Зафиксируй base commit, выбранную рабочую ветку или upgrade branch, все target worktrees, ожидаемый merge-путь, cleanup policy и expected continuation branch в `<run-dir>/03-upgrade/worktrees.md`.
- Финальная стадия `merge` обязательна как проверка доставки результата по проектной политике. Если отдельный merge не нужен, отчёт должен явно сказать почему.
- После успешного merge или project delivery перейди на expected continuation branch, обычно интеграционную ветку проекта, и проверь, что merged upgrade commit достижим из неё.

## Что докладывать

В отчёте укажи:

- текущую ветку;
- base commit;
- upstream;
- был ли рабочий каталог чистым;
- какие изменения существовали до начала;
- какая ветка или worktree использовались;
- какой merge-путь требует проектная политика и выполнен ли он;
- на какую ветку перешла сессия после merge и почему;
- какие временные ветки/worktrees удалены или оставлены с retention reason;
- какие файлы добавлены в текущую работу;
- какой commit trace tag применён или почему commit/tag не создавался;
- что осталось вне scope.

## Запреты

- Не откатывай чужие изменения.
- Не смешивай ремонт Банка памяти с unrelated кодовыми правками.
- Не делай upgrade канона поверх грязной неизвестной базы.
- Не коммить `.tasks/`, `.idea/`, локальные артефакты или чужие файлы без явного решения проекта.
