# Клиентский слой и управляемые интерфейсы

## Зачем это нужно

Если у проекта есть сервер, командная строка, текстовый интерфейс или графический интерфейс, клиентская логика не должна жить в каждом интерфейсе отдельно.

Правильная модель строится сверху вниз:

```text
серверный контракт операций
-> клиентский набор методов
-> командная строка
-> текстовый интерфейс / графический интерфейс / MCP-инструменты / сценарные раннеры
-> сценарии и стендовая приемка
```

Смысл этой цепочки:

- серверный контракт операций определяет, какие действия система поддерживает;
- клиентский набор методов содержит клиентскую логику: вызовы, ошибки, авторизацию, формат входов и выходов;
- командная строка дает самый простой способ проверить клиентский слой без браузера и сложного интерфейса;
- текстовый, графический, MCP и сценарные клиенты используют тот же клиентский слой, а не повторяют бизнес-логику;
- сценарии и приемка могут проверять систему на нужном уровне: данные через клиентский слой, видимость и действия через интерфейс.

Точное различие:

- сервер или локальное ядро предоставляет операции;
- SDK является клиентской программной границей;
- CLI/TUI/GUI/MCP и сценарные раннеры являются потребителями SDK.

API как серверная граница не "идет через SDK". Через SDK идут клиенты.

## Когда применять

Применяй эту политику, если в проекте есть хотя бы два пункта из списка:

- серверный или локальный программный интерфейс;
- клиентский набор методов;
- командная строка для людей или агентов;
- текстовый интерфейс;
- графический интерфейс;
- MCP или другой программный инструмент для агента;
- стендовая или внешняя приемка;
- сценарии, которые должны управлять системой программно.

Для маленькой библиотеки без клиентских поверхностей это правило можно не применять. Но как только появляется интерфейс для человека или агента, цепочка должна быть осознанной.

## Серверный контракт операций

Серверный контракт операций отвечает на вопрос: "что можно сделать с системой программно?"

Каждая операция должна иметь:

- устойчивый идентификатор;
- схему входа;
- схему результата;
- типизированные ошибки;
- ожидания по авторизации или контексту;
- владельца: область продукта, платформы или слоя.

Контракт операций не должен группироваться по транспорту. Например, операция не должна становиться "http-командой" только потому, что сегодня вызывается через HTTP. Транспорт можно заменить, а смысл операции должен остаться.

## Клиентский набор методов

Клиентский набор методов - это единственная поддерживаемая клиентская граница.

Он должен:

- вызывать операции из каталога;
- проверять входы и результаты;
- обрабатывать типизированные ошибки;
- подключать авторизацию и контекст;
- скрывать транспортные детали;
- оставаться тонким слоем без продуктовой бизнес-логики.

Если клиентский набор методов начинает решать продуктовые правила, он превращается во второй слой приложения. Это архитектурный дрейф.

## Продуктовый SDK как тонкий фасад

Если проект использует общий платформенный клиентский набор методов, продуктовый клиентский набор методов должен быть тонким фасадом (thin facade), а не копией платформенного SDK.

Целевая цепочка:

```text
платформенный SDK
-> продуктовый SDK-фасад
-> CLI / TUI / GUI / MCP / сценарный раннер
```

Продуктовый фасад может:

- добавлять продуктовый контекст: авторизацию, выбор рабочего пространства/профиля (workspace/profile selection), поверхность источника (source surface), идентификатор корреляции (correlation id);
- нормализовать ошибки в форму, удобную для CLI/GUI;
- группировать платформенные операции в продуктово-понятные методы;
- добавлять безопасные диагностические поля;
- скрывать транспортные детали от клиентов.

Продуктовый фасад не должен:

- дублировать DTO и схемы платформы;
- создавать второй платформенный SDK внутри продукта;
- обходить платформенную валидацию;
- смешивать продуктовую бизнес-логику с транспортной обвязкой;
- учить платформенный слой продуктовым сущностям, если они принадлежат продукту.

Это правило нужно, чтобы продукт мог сохранять свой язык и UX, но не расходился с общей платформенной границей.

## Командная строка как опорная поверхность

Командная строка нужна не только пользователю. Она особенно полезна агенту, потому что позволяет быстро проверить клиентский слой без графического интерфейса.

Командная строка должна:

- работать поверх клиентского набора методов;
- иметь стабильные команды и подкоманды;
- возвращать устойчивые коды выхода;
- иметь машинно-читаемый вывод для сценариев и агентов;
- давать короткие команды для основных проверок;
- не содержать собственной копии бизнес-логики.

Рекомендуемая практика: если новая операция должна попасть в графический или текстовый интерфейс, сначала сделать или проверить командный путь поверх клиентского набора методов. Это снижает риск, что проблема спрячется в браузере или отрисовке.

## Паритет API/SDK/CLI

Для важных операций, особенно административных, эксплуатационных и контрольных, полезен отдельный сценарий паритета API/SDK/CLI.

Он доказывает, что одна и та же способность имеет согласованное поведение через:

- защищенный прикладной интерфейс (API);
- клиентский набор методов (client SDK);
- командную строку (CLI).

Минимальная строка матрицы паритета:

- логическое действие;
- идентификатор операции API;
- метод клиентского набора методов;
- команда CLI;
- положительный ожидаемый результат;
- отрицательный результат: доступ, валидация, конфликт или готовность;
- артефакт доказательства;
- request id или correlation id.

Паритет не означает одинаковый текст вывода. Он означает одинаковую доменную семантику: что изменилось, что запрещено, какая ошибка возвращена и как это можно расследовать.

Если GUI/TUI строится поверх той же операции, UI-доказательство не заменяет паритет API/SDK/CLI. Интерфейс доказывает видимость и управляемость, а паритет доказывает клиентскую и операционную границу.

## Текстовый и графический интерфейсы

Текстовый и графический интерфейсы должны быть тонкими управляемыми поверхностями.

Они должны:

- использовать клиентский набор методов;
- иметь описанные экраны или поверхности;
- иметь стабильные идентификаторы для важных действий и областей;
- описывать состояния, роли, переходы и видимую обратную связь;
- не обходить клиентский набор методов ради "быстрой" интеграции.

Для текстового интерфейса стабильные идентификаторы могут быть идентификаторами экранов, панелей, действий, модальных окон и полей.

Для графического интерфейса стабильные идентификаторы обычно выражаются через атрибуты для тестов и автоматизации.

## Управляемый интерфейс

Управляемый интерфейс - это интерфейс, которым можно надежно управлять из сценария.

Минимальный набор для текстового и графического интерфейса:

- реестр экранов;
- спецификации экранов;
- реестр стабильных идентификаторов;
- карта "экран -> объект автоматизации";
- правила видимой обратной связи после действий;
- связь сценариев с доказательствами.

Минимальный набор для командной строки:

- реестр команд;
- стабильные коды выхода;
- машинно-читаемый формат вывода;
- связь команд с операциями клиентского набора методов;
- примеры для проверки основных сценариев.

## Слои стендовой приемки

Стендовая приемка должна разделять деловую истину и интерфейсную видимость.

Рекомендуемые слои:

- **стенд через прикладной интерфейс** - проверяем состояние и бизнес-факты через защищенный интерфейс, клиентский набор методов или командную строку поверх него;
- **стенд через пользовательский интерфейс** - проверяем маршруты, видимость, ключевые действия и стабильные идентификаторы;
- **внешняя ручная проверка** - используем только там, где нужен настоящий внешний канал, провайдер или человек.

Правило: пользовательский интерфейс не должен быть единственным источником доказательств для важной бизнес-логики, если эту логику можно проверить через клиентский слой.

## Что фиксировать в Банке памяти

Если проект использует эту политику, Банк памяти должен содержать:

- где живет контракт операций;
- где живет клиентский набор методов;
- какие клиентские поверхности считаются опорными;
- какие команды проверяют клиентский слой;
- какие экраны или поверхности являются управляемыми;
- какие сценарии проверяют клиентский слой, командную строку и интерфейсы;
- какие стендовые слои обязательны для приемки.

## Антипаттерны

- Графический интерфейс вызывает сервер напрямую, минуя клиентский набор методов.
- Командная строка и графический интерфейс реализуют одну и ту же клиентскую логику по-разному.
- Сценарии проверяют бизнес-истину только через браузер, хотя есть защищенный программный интерфейс.
- Автоматизация ищет элементы по случайному тексту вместо стабильных идентификаторов.
- Текстовый интерфейс управляется через сырые нажатия клавиш без устойчивой модели экранов и действий.
