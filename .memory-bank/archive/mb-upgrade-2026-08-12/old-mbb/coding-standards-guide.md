# Стандарты кодирования

## Зачем это нужно

MBB описывает, как вести Банк памяти. Но проекту нужен еще один слой: как писать код так, чтобы он оставался понятным, проверяемым и пригодным для работы с ИИ-агентами.

ИИ-агент особенно чувствителен к трем проблемам:

- большие файлы, где смешаны разные ответственности;
- неявные границы между доменом, транспортом, данными и интерфейсом;
- отсутствие ссылок между кодом, спецификациями, фичами и сценариями.

Стандарты кодирования не должны превращаться в вкусовой кодекс. Их задача практическая: уменьшить область догадки и сделать изменение проверяемым.

## Что стандарты кодирования НЕ заменяют

Стандарты кодирования:

- не заменяют архитектурные спецификации;
- не заменяют ADR;
- не заменяют линтер и форматтер;
- не заменяют ревью;
- не являются списком личных предпочтений.

Они фиксируют правила, которые помогают проекту оставаться сопровождаемым: как разбивать код, где держать инварианты, что документировать, какие проверки обязательны.

## Где хранить

В проекте стандарты должны жить в:

```text
memory-bank/spec/engineering/coding-standards.md
memory-bank/spec/engineering/jsdoc-docstrings.md
memory-bank/spec/engineering/testing-strategy.md
memory-bank/spec/engineering/agent-coding.md
```

Для маленького проекта допустим один файл `spec/engineering/coding-standards.md`, если он не разрастается.

## Базовые правила

### 0. Простота - обязательное качество решения

Выбирай самое простое решение, которое полностью сохраняет требуемую функциональность, проверки, безопасность и сопровождаемость.

Избыточное усложнение является дефектом, а не вкусовым замечанием. Если решение можно упростить в текущем scope без потери требуемого поведения, такое замечание нужно исправлять как bug:

- убрать неиспользуемую абстракцию, сущность, статус, поле, prompt-блок, слой или файл;
- заменить преждевременную универсальность конкретным решением для текущего подтверждённого случая;
- не вводить extension point, registry, adapter, queue, schema field или lifecycle state без текущего потребителя;
- не разбивать код или документы на дополнительные уровни, если это не уменьшает реальную сложность;
- не переносить локальное правило в общий слой, пока нет повторного использования или явного проектного решения.

Допустимая сложность должна иметь текущую причину: consumer, lifecycle, verification и понятное ухудшение без этой сложности. Если причина звучит как "может пригодиться потом", это архитектурный долг, а не основание для реализации.

### 1. Один модуль - одна ответственность

Файл должен иметь понятную причину существования.

Хорошие границы:

- доменная политика;
- прикладной сценарий;
- контракт операции;
- адаптер данных;
- транспортный обработчик;
- преобразование DTO;
- view model;
- тестовая фикстура.

Плохая граница:

- `utils`;
- `helpers`;
- `misc`;
- файл, где одновременно API, база, бизнес-правила, UI-состояние и тестовые данные.

`utils` допустим только для действительно малых, стабильных и бездоменных примитивов. Если утилита знает о продукте, она уже не утилита.

### 2. Размер файла - сигнал, а не абсолютный закон

Рекомендуемые ворота внимания:

```text
до 250 строк      # обычно нормально
250-500 строк     # проверить, не смешаны ли ответственности
500-800 строк     # кандидат на разбиение
800+ строк        # нужен план декомпозиции или явное объяснение
1000+ строк       # почти всегда архитектурный долг, кроме generated/fixtures/snapshots
```

Не нужно резать файл механически только из-за числа строк. Нужно смотреть на смешение ответственностей. Файл на 600 строк с одной ясной таблицей переходов может быть лучше, чем пять маленьких файлов с неявными связями.

### 3. Доменная логика не живет в интерфейсе

GUI, TUI, CLI и MCP-инструменты не должны становиться вторым приложением.

Целевая цепочка:

```text
серверный или прикладной контракт
-> клиентский SDK
-> CLI / TUI / GUI / MCP / сценарные раннеры
```

Интерфейс может владеть представлением, состояниями отображения и пользовательским взаимодействием. Он не должен владеть бизнес-правилами, авторизацией, схемами операций или нормализацией ошибок, если эти правила уже принадлежат серверу или SDK.

### 4. Побочные эффекты изолируются

Код легче проверять, если доменная логика отделена от:

- базы данных;
- файловой системы;
- сети;
- браузера;
- очередей;
- внешних провайдеров;
- текущего времени;
- случайности.

Практическое правило: если функция принимает данные и возвращает решение, она должна быть чистой настолько, насколько это разумно. Побочные эффекты подключаются на краях через адаптеры.

### 5. Ошибки являются частью контракта

Ошибки должны быть типизированы или хотя бы категорийны.

Минимум:

- validation;
- access/permission;
- conflict/concurrency;
- not found;
- readiness/configuration;
- provider/backend;
- unexpected.

Ошибки не должны превращаться в пустой успех. Если провайдер недоступен, это не "пустой список". Если нет прав, это не "ничего не найдено".

Для AI/model/provider runtime отдельно классифицируй сетевые ошибки, timeout, rate limit, недоступность provider-а, auth/config ошибки, неправильную схему ответа модели, semantic mismatch, tool-denied/unsafe result, stale context and partial worker failure.

Retry, backoff, fallback profile, repair prompt, `DEF-*` или blocker должны выбираться явно. Молчаливый fallback на другую модель или "успешный" пустой результат без evidence недопустим.

### 6. Тесты проверяют инварианты

Тесты должны защищать смысл, а не только текущую форму кода.

Обязательные виды проверок выбираются по риску:

- unit - чистая логика и маленькие правила;
- integration - контракты между модулями, storage, API;
- e2e - путь через систему;
- scenario - воспроизводимая приемка способности или жизненного цикла;
- regression - найденный баг или важная граница.

Если фича меняет контракт, сценарий или пользовательский путь, одних unit-тестов недостаточно.

## JSDoc и docstrings

JSDoc/docstrings нужны не для каждого helper. Они нужны там, где код является публичной или важной границей.

Документируй:

- entrypoint пакета;
- публичный SDK-метод;
- operation handler;
- доменную политику;
- state machine;
- event contract;
- сценарный раннер;
- компонент, который является владельцем поведения;
- CLI command handler or command contract;
- prompt/model/tool orchestration boundary;
- workflow, pipeline, queue or concurrency coordinator;
- persistence/runtime adapter;
- schema/config/protocol format.

Минимальный формат:

```ts
/**
 * Коротко объясняет ответственность границы.
 *
 * @docs memory-bank/spec/system/<area>/contract.md
 * @spec memory-bank/spec/system/<area>/contract.md
 * @adr memory-bank/adr/ADR-XXX-<slug>.md
 * @feature memory-bank/plans/epics/EP-XXX-<slug>/features/FT-XXX-YY-<slug>.md
 * @protocol memory-bank/protocol/PRT-XXX-<slug>.md
 * @scenario memory-bank/scenarios/SCN-XXX-<slug>.md
 */
```

Не нужно ставить все теги всегда. Ставь те, которые реально помогают трассировке.

Принятые tags для doc links:

- `@docs` - профильный документ Memory Bank, когда нужен общий вход;
- `@spec` - нормативная спецификация;
- `@adr` - решение и rationale;
- `@feature` - доставляемая capability/value record;
- `@protocol` - execution trace or remediation context;
- `@scenario` - воспроизводимая проверка;
- `@evidence` - verification passport or proof summary.

Если для публичной границы ссылка не нужна, это должно быть очевидно из локального контекста. В сомнительных случаях readiness/review может потребовать короткий `not_applicable` rationale в отчете, а не декоративный комментарий в коде.

Правило: комментарий в коде объясняет локальную нетривиальность. Документ в Банке памяти объясняет устойчивый смысл и границы.

## Агентно-дружественный код

Код удобен для ИИ-агента, если:

- важные границы имеют понятные имена;
- entrypoint показывает, куда идти дальше;
- публичные функции имеют doc links;
- тесты можно запустить локально;
- изменения можно делать в небольших областях;
- нет скрытой магии в больших глобальных singleton-ах;
- конфигурация и окружения описаны;
- ошибки не маскируются;
- генерация и ручной код разделены.

Хороший агентный стандарт не требует, чтобы агент "догадался". Он дает ему маршрут: что прочитать, что можно менять, какие проверки запустить.

Если код реализует prompt/model/tool pipeline, он должен быть агентно-наблюдаемым:

- входной prompt или prompt version понятны;
- выбранный контекст и tool results трассируются;
- model output валидируется перед потреблением;
- retry/repair behavior ограничен и воспроизводим;
- provider profile and fallback policy documented;
- deterministic code делает parsing, normalization, sorting, deduplication and schema validation вместо модели, когда это возможно.

## Правило для больших изменений

Если изменение затрагивает несколько подсистем, клиентский слой, UI, данные или rollout, не начинай с кода.

Сначала:

1. прочитать `spec/product`, `spec/system`, `spec/engineering`, `spec/operations`;
2. зафиксировать ADR, если есть архитектурный выбор;
3. подготовить spec или protocol;
4. определить сценарии и evidence;
5. только потом писать код.

Это не торможение разработки. Это способ не построить правильный код вокруг неправильной границы.

## Автоматические проверки

Проект может вводить проверки постепенно:

- предупреждения о файлах больше 800 строк;
- проверка наличия JSDoc `@docs` у публичных entrypoint;
- проверка существования ссылок из `@docs`;
- проверка запрета прямых вызовов API из GUI при наличии SDK;
- проверка `data-testid`/screen id против UI-контракта;
- проверка границ пакетов;
- проверка отсутствия запрещенных импортов между слоями.

Начинай с warning-only, если проект большой и исторический. Жесткие проверки вводи после инвентаризации.

## Источники подхода

Эти правила основаны на практиках из исследованных проектов и на современных рекомендациях для ИИ-разработки: давать агенту проектную память, узкую задачу, понятные границы, проверяемые тесты, инструкции репозитория и безопасный контур выполнения.

Канон не привязан к конкретному поставщику агента. Важен принцип: код и документация должны уменьшать неопределенность.
