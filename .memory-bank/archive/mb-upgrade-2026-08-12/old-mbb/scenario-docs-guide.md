# Scenario Docs Guide

Этот guide фиксирует, как документировать сценарии для возможностей, сквозных пользовательских путей, жизненных циклов и стендовой приемки.

## 1. Что такое scenario

Сценарий - это исполняемый контракт проверки. Он описывает не только шаги, но и цель, условия запуска, ожидаемые доказательства и критерии прохождения.

Он нужен, когда мы хотим проверить:
- platform capability;
- lifecycle block;
- canonical user journey;
- operational rehearsal платформы в подготовленной среде.

## 2. Чем scenario отличается от test

Тест:
- проверяет код, API, контракт или UI behaviour на уровне unit/integration/e2e.

Сценарий:
- проверяет, что система как инструмент реально работает end-to-end;
- использует controlled environment, fixture projects, flows, evidence collection;
- даёт verdict по capability/use case, а не только по одному куску кода.

## 3. Когда нужен scenario

Используй scenario, когда нужно проверить:
- Memory Bank bootstrap или compatibility sync;
- wanted outcome shaping;
- delivery workflow как implementation engine;
- queued merge или child-flow orchestration;
- acceptance и release/beta verification;
- plugin install или readiness flows;
- golden user journey платформы.

## 4. Типы сценариев

Рекомендуемая таксономия:

- `SCN-*` - сценарий возможности. Он проверяет конкретную способность системы: авторизация, импорт, отправка, восстановление, трассировка, клиентский контракт.
- `XE-*` - сквозной путь. Он проверяет длинный пользовательский результат, который проходит через несколько возможностей.

`XE-*` нужен не каждому проекту. Он полезен, когда одна пользовательская история проходит через несколько доменов, интерфейсов или внешних систем.

`XE-*` не должен становиться заменой всех `SCN-*`. Хорошая модель:

- `SCN-*` доказывает способность, контракт, lifecycle block или операционный gate;
- `XE-*` доказывает переживаемый актором путь, где несколько способностей сходятся в один результат.

Если сквозной путь не имеет отдельной пользовательской или операторской ценности, не заводи `XE-*` только ради крупного сценария.

## 5. Что должен содержать scenario doc

Минимум:
- `scenario id`
- `goal`
- `kind` (`capability`, `lifecycle`, `golden`)
- `preconditions`
- `fixtures`
- `phases`
- `expected evidence`
- `pass criteria`
- `supported environments`
- `verification matrix links`, если проект ведет матрицу проверки
- links на related ADR/feature/spec, если релевантно

## 6. Среды проверки

Сценарий должен явно говорить, где он выполняется.

Рекомендуемые среды:

- `local` - локальная проверка;
- `ci` - автоматический контур;
- `staging_api` - стенд через прикладной интерфейс, клиентский набор методов или командную строку;
- `staging_ui` - стенд через текстовый или графический интерфейс;
- `external_manual` - внешняя ручная проверка для реального канала, провайдера или человека.

Названия можно адаптировать, но смысл слоев должен оставаться понятным.

## 7. Связь с клиентским слоем

Если проект использует клиентский набор методов, сценарии должны выбирать самый устойчивый слой проверки:

- бизнес-факты и состояние проверяются через клиентский набор методов, командную строку или защищенный прикладной интерфейс;
- видимость, маршруты и действия проверяются через текстовый или графический интерфейс;
- ручная внешняя проверка используется только там, где автоматизация не может честно заменить внешний канал.

Это правило снижает зависимость приемки от хрупкой браузерной проверки.

## 8. Evidence-first rule

Сценарий не заканчивается только `passed/failed`.

Он должен оставлять:
- summary report;
- relevant run ids;
- evidence artifacts;
- explicit verdict;
- follow-up notes, если сценарий провалился или дал partial result.

Артефакт доказательства (evidence artifact) сам по себе не становится нормативной истиной (authority). Он показывает, что было проверено в конкретном запуске, на конкретном состоянии кода и среды. Нормативной истиной результат становится только тогда, когда владеющий документ - сценарий, спецификация, протокол или матрица проверки - явно принимает его как доказательство нужного контура.

Это важно для экспериментов, ответов модели ИИ, ручных проверок, скриншотов и временных отчетов. Они полезны как evidence, но не должны незаметно превращаться в продуктовый контракт.

Если доказательство появилось в `.tasks/` как отчёт субагента, verifier report, ручная заметка или proof summary, его нужно оформить до закрытия фазы.

Разделяй:

- артефакт запуска (runtime artifact) - сырой лог, скриншот, JSON, CI run или `.scenario-runs/...`;
- пакет проверки (proof bundle) - набор артефактов одного запуска;
- паспорт проверки (verification passport) - curated-документ в Банке памяти, который описывает запуск и его границы;
- приемочный вердикт (acceptance verdict) - решение в протоколе или матрице, что конкретный gate закрыт.

Паспорт проверки создаётся:

- в `protocol/<PRT-ID>/evidence/`, если доказательство относится к конкретной волне;
- в `evidence/<scope>/`, если оно должно жить как проектный проверочный паспорт;
- в `scenarios/<SCN-ID>.md` или `scenarios/<SCN-ID>/`, если меняется контракт сценария или состояние зрелости;
- в матрицу проверки, если доказательство закрывает feature/capability gate.

Сценарий, протокол или матрица проверки не должны ссылаться на `.tasks/...` как на evidence. `.tasks/` может быть источником для подготовки паспорта проверки, но не финальным местом хранения приемки.

## 8a. Состояния зрелости сценария

Сценарий должен различать документированность, исполнимость и принятие. Иначе команда начинает считать “есть файл” равным “поведение доказано”.

Рекомендуемые состояния:

- `planned` - сценарий нужен, но еще не описан или не готов к запуску;
- `documented` - документ есть, но исполнитель или данные еще не готовы;
- `runnable_local` - сценарий можно запустить локально;
- `accepted_local` - локальный запуск прошел, доказательства сохранены;
- `mixed` - часть поведения доказана, но есть внешний, стендовый или ручной контур;
- `accepted_staging` - стендовая проверка прошла и доказательства сохранены;
- `accepted_live_provider` - проверена живая интеграция с внешним провайдером (live provider);
- `blocked` - запуск невозможен, причина и следующий gate указаны;
- `deprecated` - сценарий заменен или больше не является приемочным.

Состояние должно называться честно. Например, воспроизведение кешированной ИИ-фикстуры может дать `accepted_local`, но не `accepted_live_provider`.

## 8b. Матрица диспозиции сценариев

Если в проекте накопились исторические, частично мигрированные или спорные `SCN-*`, не нужно механически превращать каждый из них в канонический сценарий.

Заведи `scenarios/scenario-disposition-matrix.md`, когда:

- сценариев много и часть из них устарела;
- проект переезжает между репозиториями или слоями;
- сценарии появились из разных волн и имеют разную зрелость;
- нужно отделить активную приемку от legacy recovery.

Рекомендуемые классы диспозиции:

- `canonical_flat_doc` - сценарий живет как полноценный документ в `scenarios/`;
- `id_first_anchor` - идентификатор сохраняется как значимый якорь, но плоский документ пока не нужен;
- `rewrite_before_migration` - смысл полезен, но старые формулировки нельзя переносить как норму;
- `legacy_recovery_overlay` - сценарий полезен для устаревшего восстановления (legacy recovery) или smoke-проверки, но не является главным воротом приемки (gate);
- `upstream_context` - сценарий важен как контекст вышестоящего источника (upstream context), но не принадлежит локальной приемке продукта.

Цель матрицы - не максимальное количество файлов, а поддерживаемый и честный набор приемочных сценариев.

## 8c. Историческое происхождение source-only

При миграции из старого проекта, mixed-repo или архива сценарий может иметь полезное историческое происхождение, но не быть текущим доказательством.

Используй статус `source_only`, когда:

- старый сценарий помогает понять, почему появилась текущая приемка;
- исторический сценарий является материалом для переписывания;
- старый артефакт доказывал поведение другой кодовой базы, ветки, окружения или продукта;
- идентификатор сохранен как lineage, но текущий проект еще не имеет нового запуска.

Правило: `source_only` можно цитировать как происхождение и контекст, но нельзя считать текущим `accepted_*` evidence.

В сценарии полезно иметь раздел:

```markdown
## Source Provenance

- Source anchors:
- Provenance status: `source_only`
- What can be reused:
- What cannot be imported as current proof:
```

Это особенно важно при актуализации (actualization) старого меморибанка: мы сохраняем знания, но не импортируем чужую приемку как текущую правду.

## 9. Связь с матрицей проверки

Если проект ведет матрицу проверки, каждый важный сценарий должен быть связан хотя бы с одной фичей, возможностью или группой возможностей.

Матрица отвечает на вопрос:

> Какая фича подтверждается этим сценарием и в какой среде?

Подробные правила описаны в [Verification Matrix Guide](verification-matrix-guide.md).

## 10. Runner rule

Scenario runner может быть реализован поверх `vitest`, но:
- `vitest` — это harness;
- `SCN-*` — это смысловая модель.

Документация scenario не должна превращаться в пересказ test runner API.

Если сценарий требует фаз, seed-данных, фикстур, нескольких акторов, артефактов, locks или cleanup, нужен отдельный переносимый контракт исполнителя сценариев. Он должен описывать run registry, рабочую папку запуска, bindings, phase policies, fixtures и правила очистки. Подробная спецификация описана в [Scenario Runner Guide](scenario-runner-guide.md).

Особое правило для ИИ-фикстур: если сценарий использует заранее полученный ответ модели, он должен храниться как фикстура с происхождением, входом или хешем входа, моделью, датой получения и назначением. Такой кеш проверяет воспроизводимость системы вокруг ответа, но не заменяет отдельную проверку живой интеграции с моделью.

## 11. Interface automation rule

Если сценарий включает текстовый или графический интерфейс:

- он должен опираться на контракт управляемого интерфейса;
- использовать стабильные идентификаторы;
- работать через экранные или командные действия, а не через случайный текст;
- следовать правилам из [Client Surfaces](client-surfaces.md).

## 11a. Сценарий паритета API/SDK/CLI

Если сценарий проверяет важную операционную или административную способность, он может быть паритетным сценарием API/SDK/CLI.

Такой сценарий должен проверить:

- прямой защищенный API путь;
- метод клиентского набора методов (client SDK);
- команду CLI;
- положительный результат;
- отрицательный результат: доступ, валидация, конфликт, readiness или disabled state;
- request/correlation id для расследования;
- нормализованный diff между результатами.

Паритетный сценарий не доказывает UI. Он доказывает, что клиенты поверх одной операции не расходятся по доменной семантике.

## 12. Naming rule

Используй идентификаторы вида:
- `SCN-001`
- `SCN-002`
- `XE-001`, если проект использует сквозные пути

и короткий slug/название, объясняющее цель сценария.

## 13. Practical scope rule

Не делай scenario слишком узким:
- если он проверяет только один helper method, это test, а не scenario.

Не делай scenario слишком расплывчатым:
- он должен иметь ясные pass criteria и reproducible preconditions.
