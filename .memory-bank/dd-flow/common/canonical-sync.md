# Канон, проекты и обкатка

`dd-memorybank` является repo root источника истины. В новом layout содержимое Банка памяти канона живёт в `canon_memory_bank_root = <dd-memorybank>/.memory-bank`, `dd-flow` - в `canon_flow_root`, а MBB - в `canon_mbb_root`.

Проектные копии в `.memory-bank/mbb/` являются применением MBB-канона в конкретном репозитории. Проектный `.memory-bank/dd-flow/` больше не является полной копией канона: это curated project flow pack по `common/flow-origin.md`, содержащий только project-local flows и их support-файлы.

Canonical-only flows (`mb-init`, `mb-upgrade`, `mb-upgrade-review`, `mb-distill`) запускаются из `canon_flow_root` и работают с целевым проектом через `target_project_root`. Они не должны жить активными entrypoint-ами в проектном `.memory-bank/dd-flow/`.

## Правило изменения канона

1. Новое правило, prompt-поведение, аспект, target-worker, eval или MBB-стандарт сначала проектируется в `dd-memorybank`.
2. Для проверки в проект-полигон, обычно `dd-flow-playground`, устанавливается нужный curated project flow pack или запускается canonical-only flow из канона.
3. Playground-прогон проверяет поведение агента на живом сценарии.
4. Найденные исправления возвращаются в `dd-memorybank`.
5. После стабилизации MBB-канон и project flow pack распространяются в нужные проекты через `mb-upgrade`, а canonical-only flows остаются в каноне.

Если эксперимент сначала появился в проекте, перед тем как считать его нормой, агент обязан:

- сравнить проектную копию с `dd-memorybank`;
- выделить ценное поведение;
- перенести его в канон;
- только после этого распространять в другие проекты.

## Что нельзя делать

- Нельзя чинить только project copy и считать канон обновлённым.
- Нельзя копировать из playground в другие проекты, минуя `dd-memorybank`.
- Нельзя копировать весь canonical `dd-flow/` в проектный `.memory-bank/dd-flow/`; вместо этого используй manifest-governed project flow pack.
- Нельзя сохранять противоречащие версии одного prompt-а без явного протокола миграции.
- Нельзя оставлять legacy/fallback поведение в каноне, если принято решение о новом формате.

## Как фиксировать перенос

Протокол изменения канона должен содержать:

- какие проекты сравнивались;
- какие файлы отличаются;
- какие проектные наработки подняты в канон;
- какие отличия отвергнуты и почему;
- какие проекты должны получить копию после проверки;
- какой playground/eval-сценарий доказывает поведение.

После переноса запускай `mb-lint` для канона. Если MBB или project flow pack затем распространяется в проект, запускай проектный `mb-lint` тоже.
