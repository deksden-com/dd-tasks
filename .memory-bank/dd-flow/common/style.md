# Общий стиль общения

Придерживайся этого стиля во всех фазах и переноси его в протокол, если протокол фиксирует правила взаимодействия.

## Язык пользовательских артефактов

Определи целевой язык (target language) по текущему пользовательскому prompt-у. Если пользователь явно попросил другой язык для отчёта, stage report, dashboard, документа или ответа, используй явно запрошенный язык.

На целевом языке пиши все пользовательские артефакты:

- финальные ответы агента пользователю;
- пользовательские итоговые отчёты (`final-report.md`, summary для пользователя, release/review handoff);
- stage report/dashboard content: заголовки, пояснения, tooltips, findings, next action, axis/row labels, visible sample replacement text;
- curated summaries, если они предназначены для чтения пользователем или будущим владельцем проекта.

Внутренние рабочие артефакты можно писать на английском, если это удобнее для агентов и не ухудшает пользовательскую приёмку:

- task packets для субагентов;
- промежуточные отчёты между агентами;
- технические manifests, raw evidence, machine-readable notes;
- имена полей, CLI flags, JSON keys, class names, function names, IDs and code comments, если проектный стиль этого требует.

Шаблон stage report или dashboard может оставаться на английском как исходный HTML/CSS/JS artifact, но сгенерированный пользовательский отчёт для конкретного запуска должен иметь содержание на целевом языке. Не оставляй sample/explanation text шаблона на английском, если пользовательский prompt был на русском и пользователь не просил английский отчёт.

- Если термин важен для точности, поиска по коду или связи с документацией, сначала давай вариант на целевом языке, затем английский в скобках: `запрос на слияние (pull request)`, `ворота приемки (acceptance gate)`, `клиентский набор методов (SDK)`.
- Распространенные в русском англицизмы использовать можно, но важные термины сначала раскрывай по-русски с английским вариантом в скобках. Дальше в том же документе можно использовать короткую форму, если она уже понятна из контекста.
- Объясняй планы и вопросы не только названием этапа, но и смыслом: что проверяем, зачем это нужно, какой риск снимаем.
- Когда задаёшь вопрос, предлагай варианты с мотивацией и рекомендацией. Не перекладывай выбор на пользователя, если можно сделать разумное предположение без риска.
- В докладах раскрывай логику: что было сделано, почему именно так, чем закончилось, какие доказательства есть, что осталось открытым.
- Не называй работу готовой без указания контура готовности: локально, в ветке, после интеграции, на бета-стенде (beta), в продуктовом окружении (production).
- Если что-то нельзя закрыть сейчас, называй это явно через именованное отложение `DEF-*`, а не формулировкой "потом доделаем".

## Навигационный блок отчёта

Каждый промпт, который завершает фазу, создаёт протокол, меняет состояние пайплайна или передаёт работу следующему этапу, должен включать в итоговый доклад короткий навигационный блок.

Задача блока - чтобы пользователь и следующий агент сразу понимали:

- на каком этапе пайплайна мы находимся;
- какой prompt только что закончил работу;
- с каким протоколом работали;
- что является следующим корректным шагом;
- есть ли блокеры, `DEF-*` или необходимость решения пользователя.

Формат:

```markdown
## Навигация

- prompt:
- protocol:
- current_stage:
- completed_stage:
- next_action:
- route:
- blockers:
- active_def:
- user_decision_required:
- trace_start:
- trace_report:
- run_id:
- run_dir:
- run_index:
- stage_dir:
- stage_data:
- stage_report:
- dashboard_project:
- dashboard_global:
```

Если протокола ещё нет, укажи `protocol: not_created`. Если пользователь задал исследовательский вопрос без практической задачи и протокол намеренно не создаётся, укажи `protocol: исследование - без протокола`. Если стадия неприменима, укажи `N/A` и короткую причину. Не скрывай блокеры за формулировкой "готово": если следующий шаг невозможен без ответа пользователя или `DEF-*`, это должно быть видно в навигационном блоке.

`stage_report` - HTML/Markdown completion report конкретной стадии текущего `RUN-*`. Он отличается от `dashboard_project` и `dashboard_global`: последние являются runtime dashboard-ами CLI. Целевой dashboard contract - HTML paths; markdown dashboard допускается как `dashboard_markdown_fallback` во время перехода. Если стадия не создаёт stage report, укажи `N/A` и причину.

Если используется `dd-flow` CLI и включены dashboard project/global files, указывай полные пути к HTML в `dashboard_project` и `dashboard_global`. Если dashboard отключён или CLI недоступен, пиши `N/A` и короткую причину. Эти пути нужны, чтобы пользователь или следующий агент мог открыть локальный HTML dashboard обычным кликом или через viewer.
