# План закрытия DEF

Этот промпт не запускается пользователем напрямую. Его использует оркестратор, обычно фаза `code/readiness.md`, когда нужно закрыть конкретное именованное отложение `DEF-*`.

Оркестратор передаёт тебе только операционные сведения:

- какой `DEF-*` закрываем;
- где лежит исходный протокол;
- какие документы и файлы читать;
- какие границы чтения и записи действуют;
- куда записать план;
- какие проверки обязательны.

Общие правила ты читаешь сам из этого файла и связанных правил MBB. Это снижает риск, что оркестратор забудет важную инструкцию.

Следуй `target_language`, переданному оркестратором или определённому по `common/style.md`: пользовательские summaries/final report content должны быть на целевом языке; внутренний DEF-plan может быть английским, если оркестратор затем синтезирует пользовательский слой.

## Обязательный контекст

Прочитай:

- `.memory-bank/dd-flow/common/style.md`
- `.memory-bank/dd-flow/common/memorybank.md`
- `.memory-bank/dd-flow/common/closure.md`
- `.memory-bank/mbb/named-deferrals-guide.md`
- `.memory-bank/mbb/delivery-docs-guide.md`
- `.memory-bank/mbb/verification-matrix-guide.md`
- исходный `DEF-*`;
- исходный протокол, фазу, задачу или отчёт, где `DEF-*` был создан;
- документы, указанные в `context_for_followup`, `related_files`, `required_docs`;
- кодовые пути, команды и доказательства, указанные в `context_for_followup`, если они есть.

## Задача

Сформируй grounded plan закрытия `DEF-*`: что нужно сделать, чтобы закрыть разрыв честно, какие проверки это докажут и нужен ли пользователь для снятия блокера.

## Что проверить

- действительно ли `DEF-*` ещё актуален;
- что уже было сделано;
- какие проверки уже выполнялись;
- что конкретно осталось;
- можно ли закрыть сейчас;
- блокирует ли это merge, beta, production или только дальнейший follow-up;
- зависит ли закрытие от пользователя;
- нужен ли отдельный follow-up протокол;
- достаточно ли контекста в самом `DEF-*`, чтобы новый агент мог продолжить работу.
- является ли DEF отложенной ручной проверкой (`verification_deferral`) и достаточно ли там указаны scenario, reason, next gate, blocks/does_not_block и required environment.

## Пользовательский блокер

Не привлекай пользователя к мелким техническим согласованиям.

Если пользователь действительно нужен, укажи:

- какой выбор требуется;
- почему агент не может принять решение сам;
- варианты с последствиями;
- рекомендуемый вариант.

Если пользователь не нужен, явно напиши:

```yaml
user_blocker:
  required: false
```

## Формат плана

Запиши план в путь, который передал оркестратор:

```markdown
# DEF plan: <DEF-ID>

## Контекст

- DEF:
- origin protocol:
- origin phase/task:
- related docs:
- related code:
- evidence so far:

## Диагноз

- актуален ли DEF:
- что уже закрыто:
- что осталось:
- что блокирует:
- что не блокирует:

## Пользовательский блокер

- required: true | false
- question:
- options:
- recommendation:

## План закрытия

1. ...

## Границы

- in scope:
- out of scope:

## Проверки

- команды:
- сценарии:
- документы/evidence:
- критерий закрытия:

## Verification deferral

- applies: true | false
- scenario:
- skipped_by:
- reason:
- required_environment:
- next_gate:
- blocks:
- does_not_block:
- user_confirmation:

## Риск и next gate

- риск:
- next gate:

## Вердикт

- can_fix_now: true | false
- requires_followup_protocol: true | false
- recommended_executor: main | subagent | user
```

## Ограничения

Не исправляй `DEF-*` в этой фазе. Не меняй код и Банк памяти, кроме записи плана. Если видишь, что `DEF-*` некорректен или уже закрыт, зафиксируй это в плане и объясни, какие доказательства это подтверждают.
