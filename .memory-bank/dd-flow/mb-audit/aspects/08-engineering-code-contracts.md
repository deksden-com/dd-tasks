# Аспект: инженерные стандарты и кодовые контракты

## Цель

Проверить, что инженерные правила Банка памяти помогают поддерживать агентно-дружественный код: понятные размеры, модульность, публичные контракты, тесты и ссылки из кода в документы.

## Когда запускать

- после изменения стандартов кодирования;
- перед большим рефакторингом;
- когда агенты часто плодят монолиты или дубли;
- после введения SDK, CLI, API, UI-contract или scenario runner.

## Нормативная база

- `.memory-bank/mbb/coding-standards-guide.md`
- `.memory-bank/mbb/code-contracts-guide.md`
- `.memory-bank/mbb/client-surfaces.md`
- `.memory-bank/mbb/cross-references.md`
- `.memory-bank/mbb/architectural-approaches.md`

## Что читать в проекте

- `spec/engineering/`;
- coding standards;
- package boundaries and public entrypoints;
- SDK/API/CLI/TUI/GUI/MCP docs;
- code contract packages или schemas;
- тестовую стратегию и команды качества.

## Что проверять

- есть ли проектные стандарты кодирования;
- описаны ли допустимые размеры файлов, модульность, документация кода, тесты и стиль агентной работы;
- публичные границы имеют JSDoc/TSDoc/docstrings со ссылками на документы там, где это нужно;
- кодовые контракты существуют в коде или схемах, а не только в Markdown;
- CLI/TUI/GUI/MCP и сценарии идут через клиентский SDK.

## Признаки проблемы

- в Банке памяти нет инженерных стандартов, хотя проект активно разрабатывается агентами;
- SDK и CLI расходятся по поведению;
- важный contract type описан только словами;
- публичная операция не связана со spec/ADR/scenario;
- тестовая политика не говорит, какие проверки обязательны.

## Что не считать проблемой

- не каждый внутренний тип требует отдельного code contract;
- маленький файл не обязан ссылаться на Memory Bank;
- проект может принять локальные исключения, если они явно описаны.

## Какие `DEF-*` создавать

Группа: `ENGINEERING`.

Создавай `DEF-*`, если отсутствие инженерного правила или кодового контракта приводит к повторяемым ошибкам агентов или небезопасным изменениям.
