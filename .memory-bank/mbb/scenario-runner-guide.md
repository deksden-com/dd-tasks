# Исполнитель сценариев

## Зачем нужен отдельный исполнитель

Обычные тесты проверяют код и контракты. Исполняемый сценарий проверяет, что система как продукт или платформа проходит воспроизводимый путь: подготовить данные, выполнить фазы, собрать доказательства, проверить результат и оставить след для расследования.

Исполнитель сценариев нужен, когда сценарии становятся длиннее одного теста и требуют:

- управляемых seed-данных;
- фикстур;
- нескольких акторов;
- нескольких фаз;
- графического или текстового интерфейса;
- внешних адаптеров;
- артефактов;
- безопасной очистки;
- повторного запуска без догадок.

## Основные сущности

### Сценарий

Сценарий описывает проверяемый путь.

Минимум:

- идентификатор;
- версия;
- цель;
- разрешённые среды;
- seed-профиль;
- фикстуры;
- фазы;
- ожидаемые артефакты;
- критерии прохождения.

Сценарий должен быть отделён от исполнителя. Сценарий - это проверяемый актив проекта, исполнитель - общий механизм запуска.

### Запуск

Запуск - это конкретное исполнение сценария.

Он должен иметь:

- `run_id`;
- `scenario_id`;
- `scenario_version`;
- среду;
- статус;
- владельца или инициатора;
- путь к рабочей папке;
- время начала и завершения;
- краткий итог;
- ссылку на артефакты.

### Фаза

Фаза - это детерминированный шаг сценария.

Фаза должна:

- читать входы из фикстур и состояния запуска;
- писать явные результаты;
- сохранять артефакты;
- возвращать понятный статус;
- иметь политику ошибки.

### Фикстуры

Фикстуры - это входные данные сценария.

Типовые фикстуры:

- акторы;
- организации и роли;
- ответы пользователя;
- ожидаемые результаты;
- настройки окружения;
- ответы внешних систем;
- кешированные ответы модели ИИ.

Фикстуры должны быть частью сценария, а не спрятанным состоянием в тесте.

### Seed-данные

Seed-данные переводят систему в начальное состояние.

Рекомендуемые правила:

- есть базовый системный seed;
- именованные seed-наборы могут расширять базовый seed;
- seed возвращает устойчивые handles, а не заставляет тесты угадывать идентификаторы;
- созданные сущности попадают в `bindings`;
- очистка работает по явным bindings.

### Bindings

Bindings - это карта созданных или найденных сущностей, необходимых сценарию.

Пример:

```json
{
  "company": { "id": "cmp_123", "slug": "scenario-company" },
  "actors": {
    "admin": { "userId": "usr_1", "email": "admin@example.test" }
  },
  "createdEntities": [
    { "type": "company", "id": "cmp_123" }
  ]
}
```

Если сущность создана запуском и не попала в bindings, это дефект трассировки.

## Рабочая папка запуска

Рекомендуемая форма:

```text
.scenario-runs/
  RUN-YYYYMMDD-001__SCN-001/
    run.json
    state.json
    bindings.json
    phase-01-seed/
    phase-02-action/
    phase-03-assert/
    artifacts/
```

В рабочей папке хранятся:

- состояние запуска;
- промежуточные результаты;
- артефакты фаз;
- снимки ответов;
- скриншоты;
- журналы;
- итоговые проверки.

Большие runtime-логи можно хранить вне Банка памяти. В Банк памяти публикуется паспорт проверки (verification passport): краткий проверочный документ со ссылками и итогом.

`.scenario-runs/`, `.tasks/` и другие runtime/working каталоги не являются долговечным слоем Банка памяти. После значимого запуска нужно опубликовать паспорт проверки в `protocol/<PRT-ID>/evidence/` или `evidence/`. Если runtime-артефакт нужен для расследования, паспорт проверки ссылается на него по стабильному пути, run id или внешней ссылке, но не делает рабочий каталог единственным источником приемки.

## Пакет доказательств

Успешный код выхода (`exit code 0`) не является полным доказательством. Исполнитель сценариев должен оставлять пакет доказательств (evidence bundle), который можно прочитать машинно и человеком.

Минимальный пакет:

- `proof_id` - устойчивый идентификатор доказательства;
- `scenario_id` и версия сценария;
- `run_id`;
- commit SHA и ветка, если запуск связан с кодом;
- среда и контур доказательства (evidence contour);
- итоговый verdict;
- список проверенных фаз;
- счетчики, если они важны для приемки;
- ссылки на артефакты;
- список отложений или блокеров, если есть;
- время начала и завершения.

Рекомендуемый итоговый файл:

```text
.scenario-runs/RUN-YYYYMMDD-001__SCN-001/artifacts/proof.json
```

Минимальный пример:

```json
{
  "proof_id": "SCN-001-LOCAL-20260512-001",
  "scenario_id": "SCN-001",
  "scenario_version": "1",
  "run_id": "RUN-20260512-001",
  "git": {
    "branch": "feature/example",
    "commit": "abc123"
  },
  "environment": "local",
  "evidence_contour": "local",
  "verdict": "passed",
  "provider_calls": {
    "expected": 0,
    "actual": 0
  },
  "artifacts": [
    "bindings.json",
    "phase-03-assert/assertions.json"
  ]
}
```

Если протокол или матрица проверки ссылаются на доказательство, они должны ссылаться на паспорт проверки. Паспорт содержит `proof_id`, `run_id` и путь к актуальному proof bundle или runtime artifact. Это защищает от ситуации, когда текстовый отчет говорит “пройдено”, но непонятно, какой запуск и какое состояние системы он описывает.

Если `proof.json` создан в `.scenario-runs/` или `.tasks/`, при закрытии фазы создай паспорт проверки в Банке памяти. Минимально достаточно файла вида:

```text
protocol/<PRT-ID>/evidence/VP-<proof_id>.md
```

или, если проект хранит evidence отдельно:

```text
evidence/<scenario-id>/VP-<proof_id>.md
```

Такой файл должен содержать `passport_id`, `proof_id`, `run_id`, commit, среду, verdict, ссылки на proof bundle/runtime artifacts и границы доказательства.

## Машиночитаемая спецификация сценария

Рекомендуемый файл:

```text
scenarios/<scenario-id>/scenario.json
```

Минимальная форма:

```json
{
  "id": "SCN-001",
  "version": "1",
  "name": "First useful path",
  "envPolicy": {
    "allowedEnvironments": ["local", "staging"],
    "allowConcurrentRuns": false
  },
  "seed": {
    "handle": "SCN-001-base",
    "extends": "system"
  },
  "artifacts": {
    "rootDir": ".scenario-runs",
    "retainDays": 30
  },
  "phasePolicy": {
    "defaultFailurePolicy": "fail_run"
  },
  "phases": [
    {
      "id": "phase-01-seed",
      "title": "Apply seed",
      "handler": "phase-01-seed",
      "requiredArtifacts": ["bindings.json", "assertions.json"]
    }
  ]
}
```

Файл задаёт каркас, а не заменяет код фаз.

## Кешированные ИИ-фикстуры

Если сценарий использует ИИ-модель, не всегда нужно вызывать модель при каждом прогоне.

Допускается хранить кешированные ответы модели как фикстуры, если:

- вход модели зафиксирован;
- версия модели или поставщика указана;
- ответ используется для воспроизводимой проверки;
- сценарий явно говорит, что проверяет не качество новой генерации, а поведение системы вокруг уже полученного ответа.

Рекомендуемые поля:

- `provider`;
- `model`;
- `input_hash`;
- `captured_at`;
- `response`;
- `usage`, если важно;
- `safety_notes`, если ответ влияет на пользовательский вывод.

Если цель сценария - проверить живую интеграцию с моделью, кешированная фикстура не заменяет отдельную проверку живого вызова.

### Реальные ответы модели как фикстуры

Ответы реальной модели можно использовать как управляемые фикстуры на основе реального ответа (real-response-derived fixtures), если цель - воспроизвести поведение системы вокруг уже полученного ответа.

Дополнительные правила:

- фиксируй происхождение: поставщик, модель, дата, вход или хеш входа;
- не сохраняй секреты, персональные данные и приватные пользовательские материалы без отдельного правила;
- указывай, ожидаются ли вызовы провайдера в этом запуске;
- сохраняй фактическое число вызовов провайдера в `proof.json`;
- явно различай повторное воспроизведение (replay) и проверку с живым провайдером (live provider).

Формула закрытия должна быть честной:

```text
accepted_local with provider_calls 0/0
```

не равно:

```text
accepted_live_provider
```

## Безопасность сред

Сценарий должен явно указывать разрешённые среды.

Рекомендуемое правило:

- `local` - разрешены разрушительные операции;
- `staging` или `beta` - разрешены только управляемые операции с явной очисткой;
- `production` - разрушительные сценарии запрещены.

Если shared-среда допускает сценарии, нужен замок запуска, чтобы два прогона не конфликтовали.

## Scenario-auth

Если сценарий должен управлять защищенным GUI/TUI/browser интерфейсом, не стоит завязывать автоматизацию на email-login, ручные magic links или внешнюю mailbox-инфраструктуру.

Для этого нужен сценарный вход (scenario auth): временный способ выдать агенту сессию, строго ограниченную запуском сценария.

Минимальные свойства:

- `scenario_run_id`;
- актор или роль;
- область рабочего пространства или проекта (workspace/project scope);
- TTL;
- одноразовость или политика запрета повторного использования (replay-denial policy);
- revoke по `scenario_run_id`;
- отметка аудита (audit marker), чтобы сценарная сессия не выглядела как обычная ежедневная сессия;
- запрет или доказанное отключение в production.

Минимальные команды или операции:

```text
scenario auth issue
scenario auth exchange
scenario auth revoke
scenario auth status
```

Доказательство должно включать:

- issuance без раскрытия секрета;
- успешный exchange;
- истечение срока или revoke;
- denial повторного использования, если политика одноразовая;
- production-disabled proof;
- отсутствие секретов в логах, скриншотах и артефактах.

Scenario-auth не заменяет обычную auth-модель продукта. Это операторский механизм для воспроизводимой приемки, который должен быть выключен или недоступен в production.

## Очистка

Очистка должна опираться только на явные следы:

- bindings;
- registry запуска;
- сущности, связанные с `run_id`;
- рабочую папку запуска.

Запрещено использовать основной механизм очистки вида:

- удалить всё с похожим именем;
- удалить по префиксу;
- поискать похожие записи и попробовать удалить;
- чистить вручную без записи в протокол.

Если после сценария остаётся мусор, это дефект bindings или трассировки.

## Политика ошибок

Минимальные политики:

- `fail_run` - при ошибке запуск останавливается, а артефакты сохраняются;
- `rerun_with_reset` - повтор фазы разрешён только если исполнитель умеет вернуть состояние к началу фазы.

По умолчанию лучше использовать `fail_run`: неудачный запуск сохраняется для расследования, а новый запуск создаётся отдельно.

## Командная поверхность

Исполнитель сценариев обычно должен иметь командную поверхность для агента и разработчика.

Минимальные группы команд:

```text
scenarios list/show
runs create/start/run/status/resume/delete
phases list/run
seeds list/show/apply
assertions run
artifacts dir/export
lock status/release
```

Если сценарий управляет пользовательскими сессиями, добавляется:

```text
auth issue
sessions list/revoke
```

Если сценарий проверяет внешние эффекты, добавляется:

```text
notifications list
webhooks list/replay
```

Открытый вопрос для проекта: объединять ли эти команды в общий административный инструмент разработки или держать отдельную командную поверхность для сценариев. Канон пока фиксирует обязательные группы возможностей, а не конкретное имя CLI.

## Связь с Банком памяти

В Банке памяти должны быть:

- человекочитаемый сценарий;
- ссылка на машиночитаемую спецификацию;
- описание seed-данных и фикстур;
- правила артефактов;
- связь с фичами, эпиками или возможностями;
- ссылка на доказательства прогонов;
- итоговый verdict.

Если сценарий важен для закрытия фичи или эпика, он должен быть связан с матрицей проверки.
