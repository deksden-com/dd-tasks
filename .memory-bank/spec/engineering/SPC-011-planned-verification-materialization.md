# SPC-011 — планируемые проверки и их материализация

## Цель

Планирование (`PLAN`) принимает содержательное решение о доказательстве
каждого требования (`R-*`) и критерия приёмки (`AC-*`). Движок `dd-flow` не
решает, достаточна ли проверка, и не делит её на «лёгкую» и «тяжёлую»; он
детерминированно проверяет контракт, порядок Work, проектные ограничения,
материализацию и факт исполнения.

## Единый контракт

`protocol-plan@6.checks[]` — единственный каталог проверок. Записи плана и
критерии приёмки ссылаются на него только через `check_refs`.

У проверки есть стабильный `CHK-*`, команда или алиас, цель (`purpose`),
точка исполнения (`run_at`) и доступность (`availability`). Уже существующая
обычная локальная команда может быть прямой. Существующий `@check/...` алиас
разрешается из профиля проекта и не дублирует команду в плане.

Будущая проверка (`planned`) всегда является новым `@check/...` алиасом с:

- точным `definition`;
- `provided_by` — PLAN item, который создаёт тест/скрипт и алиас;
- строгой зависимостью каждого потребителя от поставщика.

Проверка готовности (`readiness`) должна быть `available`: это итоговый gate,
а не неявная подготовка окружения перед CODE Work. `external` не запускается shell-командой и требует честно
описанного ограничения доказательства в соответствующем AC.

## Исполнение

CLI проецирует валидный план в `code-work-batch@5` и
`code-work-packet@5`. Пакет передаёт воркеру только относящиеся к его Work
обязанности, контекст, область записи, проверки и поставляемые алиасы.

`work finish` проверяет, что поставщик действительно записал ровно объявленное
определение алиаса, запускает проверки с `run_at: work` и сохраняет неизменяемые
квитанции: команду, время, stdout/stderr, fingerprint рабочего дерева и
заявленные файлы доказательств.

При закрытии CODE выполняются проверки `code`, итоговые `readiness` проверки и
обязательные проектные policy-gate.
Проверки `merge` и `release` сохраняются в том же каталоге для своих будущих
стадий; CODE не подменяет их агрегатным гейтом.

## Границы

- не вводятся второй реестр проверок, матрица доказательств или эвристический
  классификатор стоимости;
- не допускается anonymous planned shell command;
- агент не создаёт рукописные receipts или отчёты;
- основной контракт не поддерживает старый schema fallback.

## Оценка

PLAN-REVIEW оценивает связь `R/AC → Work → CHK`, уместность негативных
сценариев и граф поставщиков. CODE-REVIEW проверяет, что обещанный тест
материализован и способен доказать изменение, не дублируя обязательную CODE
verification. Judge оценивает адекватность доказательств отдельно от
исполнительской дисциплины и стоимости запуска.

Предпосылки проверки должны исполняться самой командой или поддерживаемой
проектной policy. Текст `purpose` не задаёт порядок shell-команд. Например,
локальная DB verification использует самодостаточный `@check/db-verify-local`,
а не пару «check, затем migrate» с обратным порядком в описании. PLAN-REVIEW
сопоставляет описание с фактической командой и доступностью предпосылок.

Browser specs импортируют общий `scripts/browser-fixture.mjs`: managed runner
наблюдает скользящее окно реальных завершённых шагов, не общий runtime теста.
Перед геометрической проверкой тест доказывает наличие ожидаемой поверхности и
непустого набора элементов. Пустой DOM не доказывает отсутствие перекрытий.
Навигация опирается на фактический UI и принятую спецификацию, не выдуманные
названия ссылок. Green test не заменяет содержательную оценку покрытия.

Native outcome и observation/cleanup оцениваются отдельно: прошедшие assertions
с неизвестным cleanup не являются PASS, но и не превращаются в ошибку продукта.
Generic timeout, infrastructure failure и неизвестная причина не разрешают
product repair. Review использует исходную диагностику и отмечает пределы proof;
исправления кандидатных тестов и приложения выполняет flow, не оператор EVAL.
